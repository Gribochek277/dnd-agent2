fix: actionable tool-failure messages instead of opaque 'Error: Function failed.' (#110)
An unhandled exception from a DM tool used to reach the model as MAF's generic
`Error: Function failed.` — no reason, no next step, so the model retried the
same call blindly (live repro: four StartCombat calls, ~15 minutes of thinking
before the turn timed out).

The single tool funnel (DmAgentToolProvider.Record/RecordAsync) now catches the
exception, logs the full exception (type, message, stack) to
`<TurnLogDirectory>/tool-failures-YYYY-MM-DD.jsonl` (default reports/llm-turns)
and returns an actionable `Rejected: <tool> failed (<reason>). <next step>`
result. The result starts with "Rejected:" so the turn tool-call tracker treats
the failed call as authorizing no narration.

The next step is tool-aware; for StartCombat it is state-aware:
- fight in progress -> "Combat is already active. Use AttackRoll / EndCombat."
- concluded fight   -> "Combat is already over (outcome: Победа). Start a new
  encounter with DeclareEncounter."
The outcome is recorded on IGameStateContext.LastCombatOutcome by both
combat-end paths and cleared by DeclareEncounter / a successful StartCombat.
StartCombat-in-Combat also gets the clearer refusal wording directly.

Deliberately NOT a gate (ADR-0002): no tool call is refused, only explained —
a new encounter still starts exactly as before (multi-fight tests unchanged).

Tests: reporter unit tests (reason + hint + log), provider funnel tests for the
sync and async paths (throwing dice engine / NPC generator), and the
tool-failure logger's JSONL write + never-throws guarantees.
